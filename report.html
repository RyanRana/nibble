The workload

Where an agent platform's memory actually goes

Two million live runs, eighty million transcript turns, two hundred million tool-call spans, twenty million semantic memories, and half a billion dedup keys a day. Each component was measured independently against a flushed Redis instance, comparing the layout you get by writing the obvious code against the cheapest layout that answers the same question.

Two free wins

The cheapest bytes are the ones you never had to think about

Most of the reductions above cost something: a codec to maintain, a trained dictionary to ship, a lossy quantizer to justify. Two cost nothing at all, and both were discovered by measurement rather than intuition.

Hash templates - one config line, Redis ≥ 8.10

Redis 8.10 added a template-listpack encoding that stores field names once for hashes sharing a schema. Setting hash-min-template-entries 4 took agent run state from 729 → 409 bytes per run with no application change whatsoever - and it beat manually shortening every field name to a single character (465 B), while keeping the schema readable. It is off by default.

Shard width - one constant, worth 15%

A sharded hash's listpack is a single allocation, and jemalloc rounds it to a size class. At 124 fields per shard an entry costs 166.6 B; at 128 fields the same entry costs 192.5 B. Identical data, identical encoding. This also explained an earlier confusion: per-field TTLs appeared to cost ~31 B/field when the intrinsic cost is ~10 B - the rest was the shard crossing a 4 KiB boundary.

Negative results

Four things that didn't work

These are kept in the repository deliberately. A benchmark that only reports its successes is marketing.

  • Compressing schema-packed records. Packing had already removed the redundancy; both zstd and dictionary-deflate made a 110-byte record larger. Compression and schema-packing are substitutes, not complements.
  • Bitmaps for sparse indexes. A bitmap costs the same whether 2% or 100% of its bits are set. At 2% density it lost to sharded intsets (9.4 vs 4.4 B/member); at 60% density it won by 20×. The crossover is measured, not assumed.
  • Reducing dimensions before binary quantization. REDUCE 256 + BIN came out larger than plain binary, because at 256 dimensions the projection matrix costs more than the dimensions it saves. Once you reach binary, the HNSW graph is ~80% of the cost.
  • MessagePack for queue tasks. Slightly worse than JSON - Redis streams already deduplicate repeated field names across entries, so the binary framing had nothing left to win.

The objections

Why people refuse to run Redis as a primary database

Each of these was turned into an adversarial test that first tries to produce the failure, then tries to prevent it. Every claim below is a program that exits non-zero if it stops being true.

Fixed · config only

“It loses acknowledged writes when it crashes”

True by default, and the default is genuinely dangerous. Under stock settings a SIGKILL destroyed every acknowledged write. With an append-only file enabled, none.

default (appendonly no)0 / 20,000 survived
RDB snapshots only0 / 20,000 survived
AOF, appendfsync everysec20,000 / 20,000 survived
AOF, appendfsync always20,000 / 20,000 survived

The distinction most write-ups blur: docker kill is process loss, and the kernel page cache survives it. The everysec window is an fsync window, not a write() window - so it loses nothing to a process crash, only to machine loss. Rather than assert that window, I measured it: WAITAOF blocks until a write is fsynced but does not itself trigger one, so its latency is the exposure window - p50 1,028 ms under everysec, collapsing to p50 0.33 ms under always.

Note the documented bound is wrong. redis.io says one second; the source postpones the write() by up to 2,000 ms when an fsync is already in flight. And audit no-appendfsync-on-rewrite: set to yes it silently defeats appendfsync always entirely during every rewrite.

Fixed · design discipline

“It silently deletes my data when it fills up”

The scariest failure mode Redis has, and completely real. With allkeys-lru - the policy every cache tutorial recommends - filling the instance destroyed 99.8% of durable records while reporting success on every single write.

allkeys-lru19,965 of 20,000 destroyed · 0 errors
allkeys-random17,457 destroyed · 0 errors
volatile-ttl0 destroyed · 293,855 cache keys evicted
noeviction0 destroyed · 2,181 explicit OOM errors

The fix isn't clever, just deliberate. Eviction is a per-key property in disguise, and volatile-* policies expose it: a key with no TTL is never an eviction candidate. Write primary records without a TTL, cache entries with one, and a single instance holds both safely - failing loudly, on the connection that caused it, instead of quietly shrinking.

Fixed · move logic server-side

“There are no transactions, so you can't maintain invariants”

Half true, and the true half matters: MULTI/EXEC does not roll back. Proven live - a transaction with one failing command still applied the commands around it. Do not build invariants on it.

But Redis runs a Lua script as one unit against a single-threaded core, which is stronger isolation than the READ COMMITTED most people actually run Postgres at. Sixty-four workers racing on the same agent runs, checked against four invariants:

read-modify-write (what most teams ship)69 violations · p99 10.2 ms
WATCH/MULTI/EXEC0 violations · 285 retries · p99 23.5 ms
Lua procedure0 violations · 0 retries · p99 11.3 ms

The script also enforces the legality table server-side, so a buggy client physically cannot write an illegal state - a request for succeeded → running was refused and the run stayed succeeded. It does this by patching the status byte and version counter of a schema-packed binary record in place, never decoding the other 107 bytes. The RAM optimization doesn't cost you server-side logic; it enables it.

Fixed · hybrid layout

“You can only query by key”

Obsolete - Redis 8 ships the Query Engine in the open-source build. But there is a real tension worth surfacing rather than hiding: FT.SEARCH indexes keys by prefix, so it cannot see inside a sharded hash. Sharding and the query engine are incompatible.

sharded + hand-rolled indexes205 B/run · 2.03 ms · you write it
hybrid: packed record + thin index doc519 B/run · 0.56 ms · full query language
hash per run + full FT index1,058 B/run · 0.56 ms · full query language

The hybrid is the recommendation: keep the fat record packed inside a sharded hash, and index a small document carrying only the columns you actually filter on. Same query surface, 2.04× cheaper. All three designs were checked against ground truth computed outside Redis, so a fast-but-wrong index couldn't win.

Unfixed in open source

“The dataset has to fit in RAM”

Still true, and it always has been. Tiered storage is commercial-only; the managed SSD tiers add roughly 300 µs on tier hits. The pricing also exposes a structural constraint worth designing around: on ElastiCache, synchronous durability and data tiering are mutually exclusive.

Cheap, durable, fast - pick two. Shrinking the dataset is the only lever that doesn't force the choice, which is the entire argument for the first half of this report.

Correction

The number I published to myself, then had to withdraw

My first vector benchmark reported binary quantization at 83% recall@10, with binary→int8 reranking recovering 100%. Both were real measurements. Both were close to meaningless.

Binary recall is overwhelmingly a property of the corpus, not the quantizer. Sweeping a corpus from low to full intrinsic rank with the quantizer completely unchanged:

recall@10 vs exact float32 cosine · 4,000 × 1536-d · quantizer identical throughout
Corpus rank Effective rank Contrast int8 binary bin→int8 ×10
1617.02.52100.0%83.3%100.0%
128100.03.66100.0%62.0%98.7%
768277.65.0699.3%34.7%76.7%
1536 (full)338.31.1298.7%32.0%71.3%

My original 83% was a rank-16 artifact. At rank 768 the same code measures 34.7% - within a point of Redis's own published 35.5% for Vector Sets BIN on real Word2Vec embeddings. Real text corpora live in that regime.

Two structural facts compound it: Redis Vector Sets discard the full-precision vector on insert, so no rescoring path exists inside them - and emulating one with a second key costs more than simply using int8.

Use int8. Do not use binary quantization in Vector Sets for production retrieval. int8 held between 98.7% and 100% across the entire sweep, matching every published source. That is the finding that generalizes - and the general lesson is that a compression ratio without a recall number, measured on a representative corpus, is not a result at all.

Errata

Four things this report got wrong, and what they cost

Kept visible rather than quietly patched. Every one was caught by the repo's own tests or by checking a claim against the source, and each changed a number that had already been published above.

Corrected

Two of the "Redis 8 defaults" were not defaults

The harness reset list-max-listpack-size to 128 between variants and called it the default. It is -2, which is a size cap of 8 KiB per quicklist node, not an entry count. With 1.2 KiB transcript turns that is about 6 turns per node instead of 128, so cases 02, 03 and 09 were measured in the wrong regime and re-run.

list-compress-depth 1 on transcripts1,150 → 1,444 B/turn
LIST of JSON spans171.5 → 269.1 B/span
hash-max-listpack-entries claimed 128, actually512

The 8.6× headline is unchanged, because the affected rows were not the winners. The lesson is narrower and more useful: a negative value in that config means something categorically different, and reading it as a count silently puts you in another regime.

Corrected

MessagePack is not worse than JSON for queue tasks

Reported from an early run and contradicted by the final data: msgpack measured 191.4 B against JSON's 216.6 B. It wins, modestly.

The real finding, which survived, is about streams: Redis already deduplicates field names across entries sharing a fieldset, so packing a span into one msgpack field cost 250.9 B against 168.2 B for plain fields. Check what the container does for you before optimizing the payload.

Corrected

The Bloom filter "discrepancy" was not one

Published 1.4 B/id where the theoretical figure is 1.198. Both are right: MEMORY USAGE is 1.1984, and used_memory is 1.3333 because a single 585 KiB filter rounds up to the 640 KiB jemalloc class. The published number includes the rounding, which is the cost actually paid.

Corrected

A durability run reported survivors that were stale data

An early crash test showed 4,000 of 20,000 writes surviving with persistence disabled, which is impossible. The harness removed the Docker volume before removing the container holding it, so the delete failed silently and the previous scenario's dataset was reloaded. Corrected result: 0 of 20,000.

Added since publication

Three results that were not in the first version

New

A sketch is not automatically the cheap answer

A t-digest allocates its full size at CREATE and never grows: verified at 9,864 B before and after 100,000 adds. At 5,000 samples per series it ties RedisTimeSeries (2.1 vs 2.6 B/sample), and TimeSeries is exact. Break-even is about 4,700 samples; below that the sketch simply loses.

And agent traffic is bimodal. A 0.5% timeout spike puts p99 on a near-vertical part of the CDF:

The cache survives 200 concurrent misses on one key

The test found a real race in the implementation: a waiter checks value then lease, so if the winner publishes between those two reads the waiter concludes the winner died and computes anyway. Exactly one worker in 200 hit it. Fixed by re-checking the value after finding the lease gone.

New

Sharded keyspaces can grow online

Shard counts constrained to powers of two make growth a split: with h % 2^k, incrementing k sends each key either to where it already is or to s + 2^k. Half the keys move, one shard at a time, with traffic running.

32 → 64 shards, 20,000 records10,314 moved
concurrent reads that missed0 of 97,399
duplicates left behind0

Both Lua scripts touch a single key, so the protocol needs no cross-slot transaction and stays legal on Redis Cluster. The proof also established a hard requirement: a client that never refreshes its generation cannot be made safe by any drain, so the splitter waits out a bounded staleness window and sweeps once more before declaring itself finished.

Method

How the numbers were taken

Each variant runs against a flushed instance. Memory is used_memory minus client, AOF and replication buffers, sampled after MEMORY PURGE and differenced against a baseline taken the same way. Every variant runs twice and the cheaper observation is kept, because allocator noise is one-sided - a sample can be inflated by fragmentation or a background rehash, but never deflated below the true allocation.

I deliberately avoid used_memory_dataset. Redis classifies the top-level key dictionary as overhead, and per-key overhead is precisely what half these optimizations attack; using the dataset figure would have silently hidden the single largest win.

Caveats. Single-node Docker on one laptop - no cluster, no replication, no network. Data is synthetic throughout: text is Zipf-sampled from a 20,000-word vocabulary, which is harder to compress than real prose, so the compression figures are conservative. Vectors are synthetic; see the correction above.

Prices are August 2026 list, on-demand, us-east-1, priced against the documented 25% memory reserve. They move.

docker kill proves process-crash durability. It cannot prove machine-loss durability - nothing running inside a healthy kernel can - which is why the fsync window is measured separately rather than asserted.
